## 🚨 Autonomous Agent Liability Disclaimer
`orch` operates via headless, autonomous agent loops designed to self-heal, modify codebase files, generate Pull Requests, and resolve issues dynamically. By running this software, you acknowledge that agents execute actions autonomously. The project creators accept **zero liability** for token expenses, infinite API loops, accidental data loss, or system vulnerabilities generated by autonomous actions. Always run inside a sandboxed environment.

## What it is

`agent-orch` runs the coding-agent CLIs already installed on your machine (Claude, Codex,
Copilot, Gemini, Grok, Kimi, Z.AI, and local models via `ccr`) as an author-and-auditor pair
on any git repo. One agent authors a small change on its own branch; a *different* agent
cross-audits the diff; your repo's own test suite gates it; a deterministic security scanner
that no agent can argue with gets the last word; and only then does the change **land** on
the `orch/integration` branch and update the standing pull request to your trunk. All
compute is local — orch spawns CLIs you already pay for and never sends your code anywhere
those CLIs would not have sent it anyway.

The word doing the work in that sentence is *different*. A single agent reviewing its own
output tends to agree with itself; the cross-audit exists so that a second model, with the
diff but not the author's rationalisation, has to be convinced. Whether that actually
catches defects at a useful rate is the project's central unproven assumption — see
[Limitations](#limitations-read-this-part).

## Requirements

- **Node ≥ 18** (`package.json` `engines`). Linux, macOS and Windows; CI gates every change
  on a `windows-latest` leg alongside `ubuntu-latest`.
- **At least one agent CLI on PATH**: `claude`, `codex`, `copilot`, `gemini`, `grok`,
  `kimi`, `zai` (needs `ZAI_API_KEY`, or the adapter reports itself disabled), or `ccr`
  (for local models). An `agy` adapter ships but is **hard-disabled in both seats** — headless
  `agy -p` works inside its own scratch workspace rather than the worktree, so it can neither
  author nor review (#272, #296); it never satisfies this requirement.
  If your PATH is degraded — cron jobs, git hooks and
  editor wrappers routinely drop `~/.local/bin` — orch also probes `~/.local/bin` and the
  running Node's own bin directory and spawns the CLI by absolute path.
- **`gh`, authenticated**, for anything that touches GitHub: `orch issue`, `orch pr`, and
  any run in a repo with a remote (because a landed cycle opens or updates the standing PR).
  Orch checks `gh auth status` up front and fails fast rather than dying halfway through.

## From nothing to a landed change

```console
$ npm install -g @bbk1ng/agent-orch
$ cd your-repo
$ orch init
orch: initialized (.orch/orch.yml, .orch/ORCH.md).
orch: detected: claude, codex — not found: agy (disabled: agy cannot be used: headless `agy -p` operates inside its private scratch workspace …), copilot (CLI not found: PATH + fallback dirs), gemini (…), grok (…), kimi (…), zai (disabled: ZAI_API_KEY is not set), local (ccr CLI not found: PATH + fallback dirs)
orch: tip — to auto-load orch usage each session, point your agent
  file (CLAUDE.md / AGENTS.md / GEMINI.md) at it, e.g. add `@.orch/ORCH.md`,
  or re-run `orch init --link` to wire it in for you.
```

`orch init` writes two files. `.orch/orch.yml` is the config — keys are grouped and
annotated, a live key carries its default inline, and a commented key shows the default it
would override, so the file doubles as a cheat sheet. `.orch/ORCH.md` is a usage doc written
for *agents* rather than humans; the tip is how you wire a pointer to it into your
`CLAUDE.md` / `AGENTS.md` / `GEMINI.md`, and `orch init --link` does that for you instead,
printing `orch: linked .orch/ORCH.md into …` in place of those three lines.

The detection line is the important one: `detected:` lists only agents that are both
resolvable *and* not disabled, so it never recommends a configuration the next run would
refuse. It is a single line covering *every* built-in adapter plus `local`, in
adapter-registry order, so in practice it is long — the `…` above are elisions, not orch's
own output.

Then ask for a change:

```console
$ orch task "fix the flaky login test"
▶ opened integration PR for orch/integration: https://github.com/you/your-repo/pull/12
orch: pr/claude/fix-the-flaky-login-test-48231-0: merged (agreed + green + integrated → PR https://github.com/you/your-repo/pull/12) after 1 round(s); clean unattended cycles: 1; cost 84,312 tokens, ~$0.41
```

Progress lines go to stderr with a `▶` prefix; the single summary line goes to stdout. Read
it left to right: the branch orch created (`pr/<author>/<slug>-<sid>`), the verdict, the
reason, how many **rounds** of author↔reviewer exchange it took, the running count of clean
unattended cycles, and what the run cost in tokens and dollars.

**Where the change ended up.** Not on `main`. The reviewed branch **landed** on the local
`orch/integration` branch, orch pushed that branch and opened (or updated) *the standing
PR* — one persistent `orch/integration → main` pull request — and stopped. Merging that PR
is the deliberate human checkpoint. Your trunk advances only when GitHub merges it, and
local `main` advances only by fetching origin and fast-forwarding; orch never commits,
resets, or pushes your trunk directly. To have orch merge the standing PR itself, ask for
it on the command line with `--until merged` — or, on the legacy path, set one of the two
v0.4 config keys described below.

Everything after this point is optional reading. `orch task "..."` plus a look at the
standing PR is the whole daily loop.

## The v0.5 way of working

Through v0.4, orch was a **single-pass** program: one cycle, and on any failure it wrote
`.orch/reviews/<branch>/DECISION.md` and stopped. A human had to notice, read the file,
diagnose, and re-run. v0.5 keeps every gate exactly as it was and changes only *what
happens after one fails*. It did not get more permissive.

### `--until` names a goal, not a mode

Every run command — `task`, `issue`, `pr`, `continue` — takes one flag with three values,
and it means the same thing on all four. (`review` takes it too on the current checkout; it
folds into `pr` at the cutover, see below.)

| `--until` | Orch keeps working until… | Merges? |
| --- | --- | --- |
| `ready` *(default)* | a pull request exists that still carries the commit orch reviewed and tested, and GitHub reports it mergeable with every required check green | never |
| `merged` | everything `ready` does, then merges the standing PR, bound to the head SHA it observed, and proves it landed with `git merge-base --is-ancestor` | yes |
| `once` | one pass, then stop — v0.4's behaviour, for a human watching a terminal | not by itself — but see the legacy config keys below |

"Still carries" rather than "is exactly": on the standing PR a head that moved because a
concurrent cycle landed after yours is re-pinned rather than failed, so long as your commit
is still an ancestor and the new head is the integration tip (`src/readiness.js:70-81`). A PR
somebody already merged short-circuits to ready too, provided the commit is reachable from
base. And when the landing target is the base branch itself, the goal is reached without any
PR being consulted.

`orch continue` is the one command that usually does not need the flag. A run records the
goal it was launched with, and a bare `orch continue <runId>` **inherits** it: resume a run
that was launched `--until merged` and it goes on working toward `merged`, not toward a
one-pass `once`. That is the behaviour you want by default — a resume is the same job, picked
back up, not a new and quieter one. Typing `--until` on the continue overrides the inherited
goal for that resume only, and never rewrites the record.

> **Not yet landed** (P12, #528). Two pieces of the above are still ahead of the checkout.
> First, the bare command still means `--until once` on `task`/`issue`/`review`/`pr`;
> `--until ready` and `--until merged` work but must be typed. Second, the override on
> `continue` is only half wired: goal inheritance itself is live (`src/cli.js:2911` reads
> `flags.until || priorRun?.policy?.until || "once"`), and `--until once` overrides fine, but
> `--until ready|merged` is still refused on `continue` outright (`src/schema.js:292`), so
> today you can only override *downward*. The flip of the default is part of the cutover:
>
> **Before (v0.4.x)**
> ```console
> $ orch task "add retry"          # one pass; a failure writes DECISION.md and stops
> ```
>
> **After (v0.5.0)**
> ```console
> $ orch task "add retry"          # loops toward `ready`; a failure gets a bounded recovery
> $ orch task "add retry" --until once   # the old behaviour, asked for by name
> ```
>
> **Why** — the goal moved out of the operator's head and into the command line. In v0.4 the
> command said *do one pass* and the operator held the goal ("…and I'll re-run it until the
> PR is green"); in v0.5 the command states the goal and orch holds the loop, bounded by
> `automation.maxAttempts`. That is what makes an unattended run's exit code meaningful.

There is deliberately **no config key that sets the default `--until` goal**: the goal is a
command-line argument only.

> **Not yet landed** (P12, #528). Two v0.4 config keys can still turn a non-merging run into
> a merge. Both default to `false`, but both are still read, validated and honoured when you
> set them — `main.autoMerge` merges the standing `orch/integration → main` PR
> (`src/github.js:686`, gated on every required check being green), and `github.autoMergePr`
> merges a per-cycle PR (`src/github.js:486`, `:513`, `:638`). Both are gated on `!v2Until`,

### A failure now gets a bounded automatic recovery

When a cycle fails, orch classifies the failure into a structured class — `REVIEW_STALEMATE`,
`TEST_RED`, `AGENT_QUOTA`, `REMOTE_BEHIND`, `SECURITY_FINDING` and roughly thirty more — and
looks that class up in a table (`REMEDY_TABLE`, `src/failure.js`). Each class carries **its
own ordered list** of remedies, and orch takes the first applicable one. There is no single
global ladder: `TEST_RED` tries `rebase → rotate → reauthor → ask`, but `DIFF_EMPTY` tries
`reauthor → rotate → ask` (`reauthor` before `rotate`), `REVIEW_STALEMATE` never offers rebase
at all, and `REMOTE_CHANGES_REQUESTED` offers nothing but `reauthor`.

Six remedies exist, and four of them are operator-orderable:

| Remedy | Chosen when | Orderable? |
| --- | --- | --- |
| **rebase + repair** | the base moved under the branch, a test went red, or a land hit a lock, a moved head, or an unreadable diff | yes |
| **rotate** | a seat crashed or hit a usage quota, or the same stalemate finding keeps repeating | yes |
| **reauthor** | empty diff, scope blown, changes requested on the PR, or two attempts converging on the same failing assertion | yes |
| **ask** | nothing automatic applies: post a question, poll for a reply from someone with verified write access, time out after `automation.humanWaitHours` (default 24) into exit `4` | yes |
| **integration-repair** | the standing PR went `BEHIND`, `CONFLICTING`, or CI-red | no — `ready` has no other route to its goal |
| **wait** | CI has not finished yet | no (and no executor is wired up on the current checkout, so that path stops at exit `2` instead of waiting) |

`automation.remedies` defaults to `null`, which means "use each class's own order"; setting
it to an explicit list re-prioritises the four orderable ones wherever a class offers them,
and a name left off the list is disabled everywhere. Leaving `ask` off is the one worth
thinking about — it does not make orch bolder, it makes it stop sooner: a class with nothing
left to try takes its terminal outcome instead of posting a question, which is exit `2`.
The manual walks each remedy in full, including the `automation.rotateModels` model ladder
and how a pinned model composes with it.

`automation.maxAttempts` (default `3`) caps the *attempt-consuming* remedy attempts after
the first cycle. It is not a cap on cycles. A run that goes down a remedy list can therefore
reach four cycles before the cap bites — and then go past it, because bounded free retries
re-run a whole cycle without spending an attempt, `ask` spends none either, and a human
replying `orch: retry` can grant up to `2 × maxAttempts` more. The hard structural bound is
32 remedy loops (`MAX_REMEDY_LOOPS`, `src/run-controller.js`). At the other end, a
terminal-class failure — `SECURITY_FINDING`, `POLICY_PROTECTED_PATH`, `CONCURRENCY_CAP`,
`REMOTE_AUTH`, `INTERNAL` — has no remedy list at all and stops after one cycle. Every wait
is bounded and each expiry costs an attempt — the termination bound is arithmetic, not
hopeful.

**Nothing is ever done autonomously, at any goal or config**: touching a guardrail path,
disabling or editing branch protection, force-pushing any ref, merging without binding to the
observed head SHA, taking merge authority from a chat comment (`orch: merge` is not a
command), or editing a diff to get past the security scanner.

Two of those deserve their exact shape rather than a slogan. On **branch protection**, orch
does hit GitHub's REST merge endpoint directly instead of going through `gh pr merge`, which
skips only `gh`'s own client-side mergeability precheck — GitHub still evaluates the ruleset
server-side. Where an owner has granted the merging actor a ruleset bypass, that direct merge
is what lands the PR, and orch's own green-check gate is then the thing holding it. On
**checks**, that green gate is orch's own on the `--until merged`, `main.autoMerge` and
`orch pr --merge` paths. The legacy `github.autoMergePr` path does not read checks itself; it
relies on GitHub's server-side protection, so in a repo with no required status checks it can
land while checks are still pending.

### The exit code is the contract

| Code | Meaning | What to do |
| --- | --- | --- |
| `0` | goal reached and verified | nothing |
| `1` | orch bug or environment failure | read the error; file an issue |
| `2` | the run stopped short of its goal and is resumable | `orch continue <runId>` grants a fresh attempt budget |
| `3` | blocked — a human must decide (always with a `blockedReason`, e.g. `guardrail-path`, `security-finding`, `concurrency-cap`) | decide, then re-run |
| `4` | asked a human, no answer inside the window | answer on the issue/PR, then `orch continue <runId>` |
| `64` | usage error (unknown command, bad flag, bad enum value) | fix the command line |

A scheduler can finally tell "retry later" from "never unattended" without parsing prose.
`2` is the broadest of the five: exhausting the attempt cap raises it, but so does a rotate
that finds no diverse seat left, a human-retry ceiling, a chosen remedy with no executor
wired up, and a `--until once` run that had no ladder to try in the first place. In every
case the meaning is the same: no goal reached, nothing decided against you, run
`orch continue`. The table is otherwise goal-independent — a terminal class such as a
security finding blocks at `3` whatever `--until` was asked for.

> **Not yet landed** (P12, #528). The blocked leg of that is not wired on the `once` path,
> which never enters the run controller and so never classifies the failure: it raises a flat
> `2` for *any* escalation or demotion. On the current checkout a security finding under
> `--until once` therefore exits `2` where the contract says `3`. Until the cutover, treat
> `2` from a `once` run as "a human should look".

Add `--json` to a `ready`/`merged` run and orch prints one JSON object per line, so a
supervising process can follow along without scraping the summary line. The event names
currently emitted are `run.start`, `run.resume`, `run.detached`, `merge.request`,
`merge.verified` and `run.end`. `--json` is command-scoped rather than global, and on
`task`, `issue` and `pr` it requires `--until ready|merged` unless `--detach` is also set —
the `once` path has no event stream to print. The CLI reference has the exact rule.
`--detach` runs the whole thing as a background child, logging under
`automation.detachLogDir`, and registers it so `orch dashboard` lists it.

## Which command do I want

| I want to… | Command |
| --- | --- |
| set up a repo | `orch init [--link]` |
| check my config is valid and see where each value came from | `orch config --check` (`--json` for machines) |
| add a registered agent to the rotation pool | `orch agent add <name>` |
| get an adapter written for an agent orch doesn't know yet | `orch agent add <name> --build` — see below |
| make a change I can describe in a sentence | `orch task "..."` |
| make a change already written up as a GitHub issue | `orch issue <n>` |
| audit or repair an existing PR or branch | `orch pr <number\|branch>` |
| pick up a run that hit the cap or timed out waiting | `orch continue <runId>` |
| see what is running and what happened lately | `orch dashboard` |
| let an MCP client (Claude Code, etc.) drive orch | `orch mcp` |
| write the version bump + CHANGELOG by hand after a hand-landing | `orch release "<entry>"` |
| update orch itself | `orch upgrade` (`--check` just reports) |

> **Not yet landed** (P12, #528). Three folds happen at the cutover: `orch review <branch>`
> disappears into `orch pr <number|branch>` (they already ran the same review-mode cycle);
> `orch agent build <name>` disappears into `orch agent add <name> --build`; and the
> interactive `orch config` wizard is removed, leaving the non-interactive report. On the
> current checkout the old spellings still work.

**Why `--build` stops instead of landing.** A built adapter goes through the same
author → cross-audit → test-gate cycle as any other change, but it never merges, even when
both agents agree and the tests are green: the result waits for you, on a local branch or —
under `landing: pr` — as an open pull request. That is deliberate rather than an oversight.
An adapter is the code orch uses to *spawn and drive other agents*; machine-written code that
will itself go on to run agents on your machine gets a human reading it before it is trusted.
So review the diff, then run `orch agent add <name>` to put the agent in the pool. The manual
has the full rationale and the wiring caveat.

Run commands fill a **seat** with a spec — `"<agent> [model] [effort]"`, agent required — but
not every command has both seats to fill. `task` and `issue` take `--author`/`--authors` as
well as `--reviewer`/`--reviewers`; `review`, `continue` and `pr` take only the reviewer
flags, because none of them assigns an author, and passing `--author` there is a usage error
(exit `64`) rather than a silently ignored flag. `orch --help` lists every flag,
and `docs/cli-reference.md` says which command honours which.

## Limitations (read this part)

**It is an educational artifact. Do not use it in production.** It is licensed
[PolyForm Noncommercial 1.0.0](LICENSE) — non-commercial use only — and it exists to make an
idea inspectable, not to be depended on. The autonomous-agent disclaimer at the top of this
file is not boilerplate.

**It costs real money, and v0.5 costs more.** Every round is real agent inference against
your own subscriptions or API keys. Under the old single-pass model a failure cost you one
cycle; under the default goal a failure that has a remedy list can reach four
(`automation.maxAttempts: 3` plus the first cycle) before the cap bites, each with an author
pass and one or more reviewer passes — and four is not the ceiling either, because free
retries and `ask` add cycles without spending an attempt and a human can grant more. (A
terminal-class failure, such as a security finding, still costs exactly one.) That is the
whole
reason `--until once` still exists. Per-cycle cost is printed on the summary line and
recorded in `.orch/runs.jsonl`, so the bill is visible rather than inferred.

**Nobody has shown that cross-audit works.** Every review round is appended to
`.orch/review-outcomes.jsonl` with a decision of `AGREE`, `DISAGREE` (an editorial rejection)
or `ERROR` (the reviewer crashed or stalled — not a rejection of the code). That file is the
raw material for a reviewer catch-rate measurement that has not been done. Until it is,
"a second agent audits it" is a design intention, not a demonstrated safety property. The
design work behind v0.5 was motivated by a similarly uncomfortable number: across 332
recorded runs in this repo's own history, zero completed cleanly with nobody watching.

**It cannot do several things by construction.** It will not split a work order into
sub-tasks — a run that keeps failing on scope is telling you to split the issue yourself. It
will not touch a guardrail path, so orch's own security machinery cannot be changed by an
orch run; those changes are hand-authored and hand-merged on purpose. It will not force-push,
and it will not disable or edit branch protection — where a merge lands under an owner-granted
ruleset bypass, GitHub is still the one evaluating that ruleset. It has no opinion about a
merge performed in GitHub's web UI,
because that produces no local run for it to observe. And it depends on your repo having a
test suite worth gating on: with no detectable test command it refuses to land anything and
escalates with "no test gate detected — set `test:` in orch.yml or merge manually".

**Security posture, in one paragraph.** The agents orch spawns run as *you*, on your machine,
with your credentials and your `gh` session; the sandbox is your responsibility, not orch's.
Against the risk that an agent writes something it should not, orch's last gate is
deliberately not an LLM: immediately before every **landing** — the merge of a reviewed branch
into `orch/integration`, and again inside conflict repair — it reads that branch's full
base→branch diff and runs it through a deterministic pattern scanner (`scanDiff` in
`src/security-review.js`) that flags added lines reading secrets or environment
(`process.env`, `.ssh/`, `PRIVATE KEY`, …), opening network connections, spawning
subprocesses, or touching workflow and branch-protection files. Any finding escalates the run
(exit `3`, `blockedReason: security-finding`) even when every reviewer said `AGREE` and the
tests are green — a reviewer can be talked into approving something; this check cannot. If
the diff itself cannot be read, orch fails closed. Note where the gate is *not*: the merge of
the standing `orch/integration → main` PR does not re-scan, because every commit in it was
scanned as it landed. It is a pattern scanner, not a proof: it
skips markdown and `docs/**` for the *content* scan (prose cannot execute a secret read)
while still applying the path-based guardrail floor to those paths, and the manual documents
each carve-out rather than overselling the whole. Report vulnerabilities privately through
the [Security tab](https://github.com/bbk1ng/agent-orch/security) — see
[`SECURITY.md`](SECURITY.md), never a public issue.
